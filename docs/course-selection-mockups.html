Course Selection — design options

Three layout variants for the Course Selection screen on the Score tab. All three keep the locked-in tab structure (All / Recents / Custom). They differ in how search interacts with the tabs — the central UX question we left open.

What's the same across all variants:
• Three tabs: All (catalog + customs merged), Recents (subset, sorted by last played), Custom (user-created courses only).
• A search input above the tabs that filters the visible list.
• A + Create new course affordance that's always reachable, and that becomes prominent when search returns no matches. Tapping it opens the New Course form (pre-filled with the search query, when relevant). On save, the new course is added to Custom, the user lands back here on the All tab, and the new course is pre-selected.
• Course cards: green left border default, orange when selected. Custom courses carry a small CUSTOM badge so they're identifiable wherever they appear.
• "Selected" state still drives the bottom Next → button (omitted from these mockups for clarity — focus is on the list region).

Option 1 — Search filters the active tab only

The simplest interaction model: the user picks a tab, then searches within it. Tab counts and structure stay stable while typing. Trade-off: if the user is on the wrong tab, their query "won't find" a course they know exists — they have to switch tabs and retype (or just retype).

Option 2 — Search collapses tabs (global flat results)

As soon as the user types in the search box, the tabs hide and the list flattens into a single global result set spanning all courses (catalog + customs). Source badges (CUSTOM) appear on each row so origin is still visible. Clearing the search restores the previously-active tab.

No-results: tabs stay hidden, empty state + prominent Create take center stage.
Strengths: a search query is treated as global from the user's perspective — they never miss a course because they were on the wrong tab. Less screen real-estate during search means more visible results. Source badges keep "is this mine?" answerable at a glance.

Option 3 — Search shows tab counts (global filter, tabs as pivot)

Tabs stay visible during search but their labels gain count badges (All 3 · Recents 1 · Custom 0) reflecting how many results live under each. The user can pivot tabs without retyping. The active tab still scopes the visible result list. Best UX of the three; modestly more work to implement (need to compute per-tab counts on every keystroke).

My pick

Option 3 (tab counts during search) gives the cleanest UX: tabs always serve as pivot, search works globally, and the no-results state is unambiguous. The implementation cost over Option 1 is small — just compute three filtered lengths per keystroke instead of one. Option 2 is the right fallback if the visual noise of count badges feels heavy. Option 1 is only the right call if we want to ship the simplest possible thing this iteration and accept that some users will type the same query into two tabs.

Independent of which we pick: the recently-played hint on cards ("Played 3 days ago") is worth keeping in all variants — it's the visible payoff for tracking completedRounds, and it makes the Recents tab feel grounded in real activity.
